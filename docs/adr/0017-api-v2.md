# 0017. API v2: v1's resources with the 4.0 identity, an MCP that takes numbers

- **Status:** accepted
- **Date:** 2026-10-27, last amended 2026-10-28
- **Decided by:** the brick-work session under the maintainer's delegation of 2026-10-26 (renewed 2026-10-27), inside design § 7, which the maintainer approved on 2026-10-23. The decisions are on [#113](https://github.com/Ulef1005/brick-work/issues/113) ("Scope and decisions (2026-10-27)") and recorded with the wiki-agent (Session Decisions seq 168, 170, 175)

## Context

Schema 4.0 ([0016](0016-data-model-4.md)) gives every item a Brick Work id, so v1's addressing by BrickLink `(item_type, item_no)` no longer names an item. A BrickLink number can name several items: n:m mappings, colour-scoped legs, merged items. v1 had two clients, Toni through the House API and the `lego-add` skill, plus the MCP server that is generated from the contract. All of them speak BrickLink numbers. Design § 7 sets the frame (paths by Brick Work id, number lookups, v1 answers 410) and leaves the conventions open.

## Options considered

1. **A redesigned v2.** New resources, envelopes and error codes, shaped around 4.0. Every client is rewritten, and the work is a milestone of its own.
2. **v1's resource set with the 4.0 identity.** Envelopes, pagination, filters, ETag and If-Match, idempotency, error codes, scopes and tokens stay as in `api-v1.md` § 2. Only the way an item is named changes, so a client changes only that.
3. **Keep v1 by translating numbers to ids at the edge.** Ambiguous numbers have no correct answer, and a merged id would silently move a write.

Recommendation: 2. Two clients, both already on the v1 conventions, and the § 7 table lists every change.

## Decision

v2 is v1's resource set with the 4.0 identity.

- **Addressing:** `/items/{id}` is canonical. `/sets|parts|minifigures/by-number/{no}` and `GET /lookup?provider=&kind=&key=` answer 200 with the same body, so a client needs one round trip.
- **Numbers:** the default provider for numbers is `bricklink`. A number that names several items answers `409 ambiguous` with the candidates; one that names none answers `404`, or `422 unidentified` on create.
- **Colours:** a colour in a request is in the provider's space. On `/items/{id}` paths it is a Brick Work colour id.
- **Merged items:** a merged id answers `307` to the survivor on GET (amended from 301 during M.11; the amendment is in `api-v2.md` § 2.10), and `409 merged` naming the survivor on writes.
- **Wishes:** wish ids are uuids.
- **v1:** answers 410 `api_retired`, except `/api/v1/health`, which still answers for the release tracker.
- **MCP:** generated from `openapi-v2.yaml`, and it keeps its tool names. No tool takes a Brick Work id. Item tools take `provider`, `kind` and `no` (marked `x-mcp-item` in the contract), and the adapter resolves them through `/lookup`, with the tool's colour taking part, since BrickLink links can be colour-scoped. `record_price` maps its colour the same way. Collection records (copies, stock, wishes, wishlists, storages, lots, events, jobs, orders, plans) keep their ids, taken from list tools. A 3xx is the tool's error, because neither MCP client follows a redirect.

## Consequences

- The House API pass-through, the Toni App Lego tab and `lego-add` switched by changing how they name items. They landed inside the cutover window, because v1 answers 410 after the switch and v2 fails against 3.3 before it.
- The House API passes a merged item's 307 on with `Location` rewritten to `/lego/…`, and still never follows a redirect.
- A BrickLink number with several Rebrickable targets (`3001` names RB `3001` and `3556` until a preferred link is set) answers `ambiguous`, and the caller must choose. Clients show the candidates and never guess.
- Additive fields need no new version: the catalogue entry's `theme` was added on 2026-10-28. A breaking change after the first deploy needs v3, and so does a change of the idempotency fingerprint (it carries `v: 1`).
