# 0022. Brick Work leaves Toni's World and takes the App Design Standard layout; the screenshot gate compares the built app with approved captures

- **Status:** accepted
- **Date:** 2026-11-04
- **Decided by:** the maintainer, 4 Nov 2026 via the wiki-agent ("brick work should plan it in milestone B"; the four questions answered with the session's recommendations). Supersedes the launch-kit decision of 2026-10-15 that Brick Work stays inside Toni's World

## Context

The App Design Standard (ai-wiki `app-design-standard.md`, phase 4.3) asks every app for its own neutral base and tokens, the P2 layout under `design/`, and a gate: every approved screen covered by a screenshot test, a token drift check, every moved path still served, and rendered tests that never skip silently. Brick Work still had the old layout: a Toni's World sub-brand skill, two token copies that have diverged, 770 flat frames, no screenshot tests and no drift check. Its `check.sh` skipped the Node harnesses silently.

## Options considered

1. **Screenshots against the design frames** (pixel-equal). The build was never pixel-equal to the frames, and a frame for a shipped feature lists its differences (#136).
2. **Screenshots against approved captures of the built app** per screen state, with the frames kept as the design record.
3. **Token values from the design copy** (the export's `design/sources/tokens-v2.css`) or **from the served copy** (`static/web/toni/tokens-v2.css`).

## Decision

- Option 2 for the screenshot gate. The frames stay the design record.
- The tokens take today's **served** look: no visual change in the roll-out. The design copy's differences go to the maintainer as a list.
- Rendering runs in CI too (Chrome installed in `check.yml`), and a rendered test that can't run fails unless `BW_SKIP_RENDERED=1` is set and named.
- `CLAUDE.md`'s rule "do not edit files in `design/`" becomes "`design/sources/` is the design project's export; `design/` is organised per P2 by scripts".
- Planned as #158–#161 (D1–D4) in milestone B, with a line in gate #96.

## Consequences

- The neutral base (design builder `base/tokens.css`) loads before Brick Work's layer. It only adds custom properties Brick Work doesn't use yet (checked 4 Nov), so no computed value changes.
- Served `/static/brickwork/...` files become generated from `design/`, and old URLs keep answering.
- B's close-out moves after D3/D4.

## State after D2 (#159)

The kit's brand panel and specimen pages moved there from the skill; their token link now points at the file beside them.
- `design/screens/NN-<screen>/` has one folder per `frames.json` section (57): the PNGs as `NN-<Screen>[-<state>]-<width>-<light|dark>.png` and the section's static HTML. `design/screens/manifest.json` is generated by `scripts/design_screens.py`; its `check` is in `scripts/check.sh`. 44 iPad frames of an earlier 10a section, listed by no section, wait in `design/screens/_unmapped/`. *Amended 2026-11-05 (maintainer: "Retire them"):* they are retired to `design/screens/_retired/`, and the brand panel and specimen pages, which came from the design skill rather than the design export, moved from `design/sources/` to `design/components/`. The app's build captures are `design/screens/approval/`.
- `design/logo/`, `design/app-icon/` and `design/components/icons/` hold the brand sources. The served `/static/brickwork/...` files stay at their paths and are generated byte for byte by `scripts/brand_assets.py build`; its `check` is in `scripts/check.sh`. `brick-work.css` and `manifest.webmanifest` are the app's own and stay in `static/brickwork/`. `tests/test_brand_assets.py` asserts every URL served before D2 still answers with the same bytes, and that path-like parameters never reach a file. No handler with a path argument was added.
- `design/DESIGN-CHECK.md`, the skill (which points at `design/` and holds no copy) and `CLAUDE.md` name the new paths.

Left for later: re-rendering the icon and splash PNG sizes from the SVG sources, one preview page per component in `design/components/`, and a rename of the 10a frames into a section if the design project adds one.

## State after D3 (#160)

- **Rendered tests never skip silently.** A test that needs node or Chrome fails when the tool is missing. `BW_SKIP_RENDERED=1` turns that into a skip; `tests/conftest.py` records every such skip and `scripts/check.sh` ends with a "Skipped rendered tests" block naming them (zero says so). `check.sh` also fails its Node harness step when node is missing, unless the variable is set. The three tests that were opt-in behind `BW_COLLECTION_CHROME` (`test_collection_screens`, `test_shell_49f`, `test_bw_planning`) now always run; the variable only points them at a Chrome binary. Two had gone stale unseen and were brought up to date: the Collection geometry test expects the coverage captions that came with M.8e, and the planning geometry test no longer measures the Prices screen, whose rows the browser builds since #24 (covered by `toni_bw_prices_runtime.cjs`).
- **The browser.** `scripts/chrome.py`: `CHROME`, else the pinned Chrome for Testing 157.0.8103.38 in `~/.cache/brickwork/chrome/<version>/` (downloaded on first use, SHA-256 checked, linux64 and mac-arm64), else a system Chrome. No npm packages.
- **Render in CI.** `check.yml` caches that directory and runs `check.sh` as before; CI never sets `BW_SKIP_RENDERED`.
- **The gate.** `design/screens/states.json` (hand-kept) says how each of the 57 sections is reached in the built app and whether it is `built` and `approved`; `scripts/screen_gate.py` makes the candidates and compares the approved states (`tests/test_screen_gate.py`); `design_screens.py check` keeps the file and `design/screens/approval/baselines/` consistent. Every `approved` is false: 33 states are built and await the maintainer's review, 28 are not built or not reached yet (each says why in `states.json`). A built state that is not approved has no baseline file in the repo; an approved state has all six. The gate reports 0 differ trivially until the first approval.
- **Baselines are made where the gate runs.** Review images for the maintainer may be rendered anywhere. At approval the session runs the `baselines` workflow (`baselines.yml`, `workflow_dispatch`) on ubuntu-latest for the approved screens, downloads the artifact and commits those PNGs with the `APPROVALS.md` line and `approved: true`, in one commit. The gate compares in CI on Linux; a local macOS `compare` differs slightly and is not authoritative: there the gate test prints its differences as advisory and passes, and only a Linux run fails on them (`BW_GATE_STRICT=1` forces it elsewhere; changed 2026-11-05, when the first 33 states were approved and every local macOS gate failed). A failing CI run uploads `build/screen-diffs/` as the `screen-diffs-1`, `-2` or `-3` artifact (one per shard job, #364).

Left for later: the first approval (the maintainer's, through a review artifact); scripted interaction for the states that need it (edit sheet, filter panel, checker steps, sheets); fixtures for the states the demo dataset cannot reach (orders, lots, instructions and boxes, a watched price, several currencies).

## State after #268

The gate has three worlds. `demo` is the dataset of the approved baselines and is never extended. `showcase` (the exported demo's invented collection) and `extras` (the showcase plus `brickwork/demo/gate_extras.py`) hold the data the later states need: orders, a lot, copies, staged checks, an instruction, boxes and a dollar wish. 39 more states are built as candidates (the maintainer approves them); a page another state already shows is recorded with `covered_by`, and the price watch (45) and the barcode scanner (57) are not in the app, so they stay unbuilt with that reason.
